# 轻量级个人待办助手 - 技术说明（更新版）

## 一、已确认的选型与约定

| 项 | 选择/约定 |
|----|-----------|
| 后端 | Node.js + Express |
| 前端 | 纯 HTML + 原生 JS + 少量库（如 SortableJS），库通过 npm 安装，用户仅需 `npm install && npm start` 开箱即用 |
| 四象限拖拽规则 | 横轴=紧急性，纵轴=重要性；拖拽后根据「横轴前一个事件的紧急性」「纵轴前一个事件的重要性」各 +1 得到新值（见下节） |
| 列表排序 | 三种模式（下拉选择）：按紧急性 / 按重要性 / 按系数；系数公式：得分 = 系数×紧急性 + (1-系数)×重要性，默认系数 0.33 |

---

## 二、前端依赖与开箱即用方案

- **SortableJS**：通过 `npm install sortablejs` 安装。
- **开箱即用**：用户只装 Node，解压 zip 后执行 `npm install` 和 `npm start`，不跑前端构建、不配环境。
- **实现方式**：
  - 在 `package.json` 的 **postinstall** 脚本中，将 SortableJS 的 UMD 文件（如 `node_modules/sortablejs/Sortable.min.js`）复制到项目的 `public/vendor/` 目录。
  - 前端 `index.html` 通过 `<script src="/vendor/Sortable.min.js">` 引用。
  - 用户执行 `npm install` 后自动得到 `public/vendor/` 下的脚本，无需 CDN、无需打包工具。

若有其他轻量库（如日期选择），同样用 npm 安装 + postinstall 复制到 `public/vendor/` 即可。

- **jsMind**：思维导图库，用于「待办脑图」功能。通过 CDN 引入（如 `https://unpkg.com/jsmind@0.8.7/` 的 style/jsmind.css 与 es6/jsmind.js），无需 postinstall。脑图为附在待办上的**纯文字节点树**，不关联其它待办；每个待办可有 0 或 1 个脑图，以 JSON 字符串存于待办字段 `mindmap`。

## 三、脑图（可选）

### 3.1 定位与数据

- 每个待办可附带一个**可选的脑图**，用于整理该待办相关的思路、子项或备注（纯文字节点树，不映射为子待办）。
- **数据模型**：待办增加可选字段 `mindmap`（字符串），存储 jsMind 的 `node_tree` 格式的 JSON 字符串；无脑图时为 `null` 或不设。
- **后端**：在 store 的 add/update 中读写 `mindmap`，与现有 CRUD 一致；GET/PATCH 时 mindmap 原样返回或提交。

### 3.2 前端交互

- **入口**：在编辑/新建待办弹窗中增加「设置脑图」按钮；点击后打开**独立脑图编辑弹窗**（避免主弹窗过大）。
- **脑图弹窗**：内嵌 jsMind 容器，可拖拽右下角拉大窗口；支持 **Insert / 回车** 新增节点、**Delete** 删除节点；关闭前无自动保存，需在**主弹窗点击「保存」**时一并提交脑图数据。
- **保存**：提交待办时从 jsMind 取 `get_data('node_tree')`，序列化为 JSON 写入请求体 `mindmap`，与标题、描述等一起 PATCH/POST。

## 四、浏览器告警（Web Notifications）

- **目的**：当有待办新进入「已过期」或「即将到期」时，通过系统/浏览器通知提醒用户，即使用户未聚焦在当前标签页。
- **入口**：页面顶部提供「开启提醒」按钮，点击后请求 `Notification.requestPermission()`；用户授权后生效。
- **触发时机**：
  1. **新进入告警**：与「已过期」「快要到 deadline 了」列表对比上一轮结果，若有**新出现的**待办 id，则发送一次浏览器通知（标题如「🪦 待办已过期」「⏰ 待办即将到期」，正文为待办标题列表）。
  2. **周期提醒**：每 5 分钟若当前仍有已过期或即将到期的待办，再发送一次「⏰ 截止告警提醒」，避免遗漏。
- **实现**：使用标准 [Web Notifications API](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API)；不支持或用户拒绝权限时不发送。通知可点击聚焦窗口并关闭。

## 五、四象限与拖拽赋值规则（核心）

### 5.1 数据来源

- 用户新建/编辑待办时输入：**待办描述、重要程度 1–10、紧急程度 1–10**（以及子任务等）。
- 这些值直接参与：列表排序、四象限落点、拖拽后的重新计算。

### 5.2 横轴 = 紧急性，纵轴 = 重要性

- **横轴前一个事件**：在「紧急性」维度上，位于当前落点左侧的参考事件（紧急性取值来自该事件）。
- **纵轴前一个事件**：在「重要性」维度上，位于当前落点上方/前面的参考事件（重要性取值来自该事件）。
- **拖拽后赋值**：
  - 新紧急性 = 横轴前一个事件的紧急性 + 1（无前一个时视为 0，即新值 = 1）。
  - 新重要性 = 纵轴前一个事件的重要性 + 1（无前一个时视为 0，即新值 = 1）。
  - 两者均限制在 1–10 范围内。

示例：横轴前一个事件紧急性为 5，纵轴前一个事件重要性为 3 → 该待办更新为紧急性 6，重要性 4。

### 5.3 界面形态：10×10 网格 + 四象限分区

为能明确得到「横轴前一个」和「纵轴前一个」，采用 **10×10 网格**（纵轴=重要性 1–10，横轴=紧急性 1–10）：

- 每个格子对应一个 (紧急性, 重要性) 坐标，例如格子 (6, 4) 表示 紧急=6、重要=4。
- 拖拽到某格子即：该待办的紧急 = 列号，重要 = 行号（与「前一个+1」等价：列 6 的横轴前一个为列 5→5+1=6；行 4 的纵轴前一个为行 3→3+1=4）。
- 在界面上用粗线标出「高/低」分界（例如 5–6 之间），形成**四象限**：
  - 第一象限：高紧急(6–10) × 高重要(6–10)
  - 第二象限：低紧急(1–5) × 高重要(6–10)
  - 第三象限：高紧急(6–10) × 低重要(1–5)
  - 第四象限：低紧急(1–5) × 低重要(1–5)

同一格子内可有多条待办，按需展示为列表或堆叠；拖拽到新格子即调用后端 `PATCH /api/todos/:id` 更新该待办的 `urgent`、`important`。

### 5.4 后端接口

- 拖拽落点确定后，前端发送：`PATCH /api/todos/:id`，body 如 `{ "urgent": 6, "important": 4 }`。
- 后端只做校验（1–10）与持久化，不参与「前一个」计算（前一个逻辑由前端根据网格位置得出）。

## 六、列表排序的三种模式

列表（推荐处理顺序）提供**下拉框**切换三种排序方式：

| 模式 | 说明 |
|------|------|
| 按紧急性 | 按 `urgent` 降序（紧急的在前） |
| 按重要性 | 按 `important` 降序（重要的在前） |
| 按系数 | 得分 = 系数×紧急性 + (1-系数)×重要性，按得分降序；**默认系数 0.33**（约 1/3 紧急 + 2/3 重要） |

- 系数可固定为 0.33，或通过同一页面上的输入框/配置项可调（初版可先写死 0.33）。
- 列表数据由后端根据当前排序模式计算后返回，或由后端提供「原始列表」+ 前端按模式排序（为减轻后端逻辑，也可前端排序；若希望服务端统一口径，则后端提供三种接口或一个带 `sortBy` 参数的接口）。

推荐：**后端提供** `GET /api/todos/list?sortBy=urgent|important|score&scoreFactor=0.33`，返回已排序的列表，便于以后加过滤、分页等。

## 七、数据模型与存储

- **TodoItem**：id, title, description, important(1–10), urgent(1–10), status, parentId, mindmap（可选，脑图 JSON 字符串）, createdAt, updatedAt 等。
- **存储**：单文件 `data/todos.json`，结构如 `{ "version", "lastUpdated", "todos": [] }`。
- **运行态**：内存缓存 + 定时落盘（如每 5 秒 dirty 则写回 JSON），保证单进程下数据一致且用户无需装数据库。

---

## 八、前端页面结构（简要）

- **顶部**：新建待办、**「开启提醒」**（请求浏览器通知权限，用于截止告警）、排序模式下拉（按紧急性 / 按重要性 / 按系数）、可选系数输入（若做可配置）。
- **左侧**：推荐处理顺序列表（可拖拽排序顺序，若后续要支持「手动固定顺序」可在此扩展）。
- **右侧**：四象限视图 = 10×10 网格 + 四象限分区线，待办可拖拽到格子内，落格即更新紧急/重要并请求 PATCH。
- **点击某待办**：弹窗编辑详情（描述、重要、紧急、链接、日期/时间、倒计时、**设置脑图** 等）；「设置脑图」打开独立脑图弹窗，使用 jsMind 编辑，保存待办时一并提交脑图数据。

## 九、实现时的模块划分（建议）

1. **后端**
   - 持久层：JSON 读写、内存缓存、定时写回；TodoItem 支持 mindmap 字段。
   - 路由与控制器：todos CRUD、列表接口（支持 sortBy、scoreFactor）。
   - 服务层：排序逻辑（按 urgent / important / score）。
2. **前端**
   - 静态资源：`public/` 下 index.html、样式、app.js；`public/vendor/` 由 postinstall 写入 SortableJS；jsMind 通过 CDN 引入。
   - 列表区：请求列表、渲染、SortableJS 列表拖拽（若需要可在此扩展顺序上报）。
   - 四象限区：10×10 网格渲染、拖拽落格、计算 (urgent, important) 并调用 PATCH。
   - 新建/编辑：表单与提交、调用 POST/PATCH；编辑内「设置脑图」打开脑图弹窗，jsMind 初始化/加载/保存，提交时带 mindmap。
